# Приёмник событий с очередью обработки

Python 3.11+, Flask, SQLite. Сервис принимает события, отдельный worker обрабатывает очередь из базы.

## Запуск

В PowerShell из папки проекта:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m flask --app event_receiver:create_app run
```

Во втором терминале из той же папки:

```powershell
.\.venv\Scripts\python.exe -m flask --app event_receiver:create_app worker
```

База `instance/events.sqlite3` создаётся автоматически. Другой путь можно задать переменной `DATABASE` в обоих терминалах. Для обработки одной задачи есть флаг `worker --once`.

## Проверка

```powershell
.\.venv\Scripts\python.exe -m pytest -q
```

Пример запроса:

```powershell
$body = '{"event_id":"abc-123","type":"payment_succeeded","payload":{"amount":100}}'
Invoke-RestMethod http://127.0.0.1:5000/webhook -Method Post -ContentType application/json -Body $body
Invoke-RestMethod http://127.0.0.1:5000/stats
```

Новое событие получает 202, повторный `event_id` — 200. Исходное событие при повторе не меняется. Ошибки тела возвращаются в поле `error` с кодом 4xx.

Обычные типы (`payment_succeeded`, `payment_failed`, `user_registered`) пишутся в лог. Для проверки ошибок: `simulated_flaky` падает дважды и проходит на третьей попытке, `simulated_failure` падает всегда. Неизвестный тип получает `skipped`.

## Решения

- Событие и задача сохраняются одной транзакцией. Уникальные ключи защищают от дублей, в том числе при одновременных запросах.
- Всего три попытки, паузы между ними — 2 и 4 секунды. После третьей ошибки задача получает `failed`.
- Worker захватывает задачу на ограниченное время. После его падения другой worker или перезапуск восстановит обработку. Токен захвата защищает от записи устаревшего результата.
- Обработчик выполняется в отдельном процессе: зависшую функцию можно остановить по тайм-ауту (по умолчанию 5 секунд). Задачи старше суток получают `skipped`.

Восстановление требует запущенного worker и доступной базы. При реальных внешних действиях нужна идемпотентность по `event_id`: падение между действием и записью результата может привести к повтору. История отдельных попыток не хранится — только их число и последняя ошибка.
